# Hush 요구사항 정의

- 작성일: 2026-10-01
- 대상: 회사 동료 두 사람이 사용하는 macOS CLI 채팅 프로그램
- 문서 상태: 현재 대화에서 합의한 기능과 정책의 기준
- 구현 상태: 도메인 규칙, 암호화 UDP 송수신·반복 송신, 비밀번호로 보호하는 기록 저장, 채팅·수신 CLI, 서명 검증 자동 업데이트·재인증 재시작과 로컬 통합 검증이 준비되고 사내 GitLab에 0.4.0을 게시한 상태이며, 두 Mac·터미널 환경 검증은 아직 완료되지 않음

이 문서는 요구사항과 사용자 관점의 동작을 정의한다. 특정 라이브러리, 파일 구조, 암호화 알고리즘 또는 프로세스 실행 방식까지 승인한 구현 설계서는 아니다. 이후 구현 전에는 프로젝트 규약에 따라 중요한 선택지와 권장안을 설명하고 결정한다.

합의한 코드 구조와 DDD·TDD 개발 규약은 [개발 규약](development.md)을 따른다.

## 1. 목적과 범위

Hush는 사내망에 연결된 두 사람이 터미널에서 메시지를 주고받는 1:1 채팅 프로그램이다. 별도 채팅 서버 없이 암호화된 메시지를 브로드캐스트하고, 같은 통신용 대칭키를 가진 상대가 복호화한다.

기본 사용 방식은 다음과 같다.

1. 두 사람이 같은 내부 네트워크에서 Hush를 사용한다.
2. 각 사용자는 자신의 개인 비밀번호로 Hush를 실행한다.
3. 채팅 화면에서 상대의 IP와 채팅용 프로세스의 실행 상태를 확인한다.
4. 메시지를 보내면 같은 메시지를 짧은 시간 안에 세 번 브로드캐스트한다.
5. 수신한 메시지를 복호화하고 중복을 제거한 뒤 표시·저장한다.
6. 채팅 화면을 닫아도 백그라운드 수신기가 동작 중이면 메시지를 받아 저장한다.
7. 이후 비밀번호를 입력해 Hush를 다시 열면 로컬에 저장된 대화를 조회한다.

사용자는 두 명을 전제로 한다. 브로드캐스트 자체가 수신 대상을 두 대로 제한하는 것은 아니며, 이 정의는 두 사람이 같은 통신용 키가 내장된 프로그램을 공유하는 사용 환경을 전제로 한다.

## 3. 사용 환경과 네트워크 전제

### 3.1 macOS와 터미널

- 두 사용자 모두 Mac에서 실행한다.
- iTerm2와 VS Code 통합 터미널에서 사용하는 것을 고려한다.
- 터미널별 입력·출력 및 시각적 표시의 구체적인 지원 방식은 구현 시 확인한다.
- 지원할 최소 macOS 버전과 Apple Silicon·Intel 배포 범위는 아직 정하지 않았다.

### 3.2 내부망 통신

- 채팅 메시지를 중계하는 서버는 두지 않는다.
- 각 Hush가 메시지를 브로드캐스트하고 상대의 메시지를 수신한다.
- 일반적인 ipTIME 공유기의 같은 기본 내부망에 연결된 두 PC를 사용 예로 삼는다.
- 해당 내부망 안에서의 통신이므로 외부 접속용 포트포워딩은 요구하지 않는다.
- 사내망 전체를 하나의 브로드캐스트 범위로 간주하지 않는다.
- 게스트 네트워크 격리, VLAN 분리, 무선 통신 차단 또는 PC 방화벽에 따라 통신이 제한될 수 있다.
- 실제 공유기와 두 Mac에서의 송수신 가능 여부는 구현 후 해당 환경에서 검증한다.

암호화·복호화는 Hush가 담당한다. 공유기에 Hush 전용 암호화 기능을 설정하는 구조가 아니다.

### 3.3 업데이트 배포와 채팅의 구분

사내망 배포 주소는 버전 정보와 프로그램 파일을 제공하는 용도이다. 이는 채팅 메시지를 중계하는 서버와 별개의 역할이며, 채팅 통신은 계속 브로드캐스트로 수행한다.

실제 배포 URL, 접근 방식, 버전 정보 형식과 배포 파일 형식은 구현·배포 단계에서 결정한다.

## 4. 참여자 식별과 메시지 표시

### 4.1 IP 기준 식별

- 참여자 표시는 수신 패킷의 출발 IP를 기준으로 한다.
- 별명이나 개인 계정을 기준으로 참여자를 표시하는 요구는 현재 범위에 없다.
- IP는 접속 주소의 식별값이며, 사람의 신원을 인증하는 수단으로 정의하지 않는다.

표시 예시:

```text
[192.168.0.34] 안녕하세요
[192.168.0.35] 네, 확인했습니다
```

같은 IP의 세션은 같은 참여자로 보일 수 있으며, 할당된 IP가 바뀌면 표시 주소도 바뀐다. IP 변경 후 기존 로컬 기록에서 내 메시지를 어떻게 구분할지는 구현 시 정할 항목이다.

### 4.2 내 메시지 하이라이트

- 내가 보낸 메시지는 상대의 메시지와 시각적으로 구분한다.
- 메시지 내용과 발신 IP 표시는 유지한다.
- 색상이나 굵기 등 구체적인 스타일은 아직 결정하지 않았다.
- 같은 메시지를 반복 전송하거나 다시 수신하더라도 화면에는 중복 표시하지 않는다.

### 4.3 새 메시지의 시각적 표시

- 새 메시지가 왔다는 것을 터미널에서 조용하게 알아볼 수 있으면 된다.
- 소리나 macOS 시스템 배너는 현재 요구사항이 아니다.
- iTerm2의 새 출력 표시와 VS Code의 시각적 bell 같은 기능을 활용하는 방향을 검토했다.
- iTerm2의 새 출력 표시는 메시지뿐 아니라 일반 로그 등 새 출력에도 반응할 수 있다.
- VS Code의 시각적 bell은 표시 시간이 있는 방식이며, 읽을 때까지 유지되는 미확인 메시지 표시와 동일하지 않다.

이 문서에서는 터미널별 표시 수단을 하나로 고정하지 않는다. 설정 안내 필요 여부와 실제 동작 방식은 구현 시 정한다.

채팅 화면이 닫혀 있을 때 백그라운드 수신기가 메시지를 저장하는 것과, 터미널에 시각적 표시를 보여주는 것은 구분한다. 닫힌 화면을 자동으로 열어 알리는 기능은 합의하지 않았다.

채팅 화면이 닫혀 있는 동안의 새 메시지는 백그라운드 수신기가 메뉴 막대에 표시한다.

- 평소에는 흑백 말풍선 아이콘으로 수신기가 실행 중임을 보여 준다.
- 기록에 아직 합쳐지지 않은 메시지가 있으면 빨간 배지로 건수를 보여 주며, 읽을 때까지 유지한다.
- 건수만 표시하고 내용과 보낸 사람은 표시하지 않는다.
- 소리, 깜빡임, 알림 센터 배너는 사용하지 않는다.
- 메뉴에서 사용자가 선택할 때만 터미널에서 Hush를 연다.

## 5. 메시지 송수신과 중복 처리

### 5.1 송신 흐름

1. 사용자가 메시지를 작성한다.
2. 해당 메시지의 최초 생성 시각과 내용 해시를 정한다.
3. 통신용 공유 대칭키로 메시지를 암호화한다.
4. 같은 메시지를 1초 동안 총 세 번 브로드캐스트한다.
5. 내 메시지를 한 번 표시하고 로컬 기록에 보관한다.

세 번의 전송은 한 메시지의 반복 송신이다. 이후에도 매초 계속 전송하는 방식은 아니다.

반복 송신은 송신 시작 시각을 기준으로 시작 시점, 0.5초 후, 1초 후에 한 번씩 계획한다. 메시지의 최초 생성 시각은 송신 시작이 늦어지더라도 유지한다.

### 5.2 수신 흐름

1. 브로드캐스트 패킷을 수신한다.
2. 패킷의 출발 IP를 확인한다.
3. 공유 대칭키로 메시지를 복호화하고 변조 여부를 검증한다.
4. 중복 판별 기준으로 이미 처리한 메시지인지 확인한다.
5. 처음 받은 메시지만 한 번 저장하고, 채팅 화면이 실행 중이면 표시한다.

복호화 또는 검증에 실패한 내용을 정상 메시지로 표시·기록하지 않는 것을 암호화 통신의 조건으로 둔다. 오류 안내 방식은 아직 정하지 않았다.

### 5.3 중복 판별 기준

```text
발신 IP + 최초 생성 타임스탬프 + 내용 해시
```

- 반복 전송하는 세 패킷은 동일한 메시지 식별값을 유지한다.
- 타임스탬프는 최초 생성 값을 유지하고 반복 전송마다 갱신하지 않는다.
- 수신 측은 첫 번째로 받은 메시지만 처리한다.
- 같은 내용을 나중에 새로 작성한 메시지는 반복 전송본과 구분해야 한다.
- 서로 다른 발신자의 동일한 내용도 구분해야 한다.
- 중복 판별 정보는 해당 대화 기록을 보관하는 동안 유지한다.
- 재시작 후 비밀번호로 기록을 연 뒤 저장된 메시지의 식별값으로 중복 판별 상태를 복원한다.

타임스탬프 정밀도, 해시 알고리즘, 동일 시각·동일 내용의 별도 메시지 구분은 아직 정하지 않았다.

### 5.4 전달 보장 범위

- 수신 확인을 받아 성공 여부를 보장하는 방식은 사용하지 않는다.
- 송신 측의 반복 전송은 총 세 번으로 끝난다.
- 세 번 모두 수신되지 않으면 해당 메시지는 누락될 수 있으며, 사용자는 이를 허용했다.
- 세 번 반복 전송은 누락 가능성을 줄이는 방법이지 전달 보장 정책은 아니다.
- 양쪽 기록에 같은 메시지가 항상 모두 존재한다고 가정하지 않는다.

백그라운드 수신이 동작하지 않던 동안의 메시지를 이후에 자동 복구하는 요구는 현재 정의되지 않았다.

## 6. 채팅용 역할과 백그라운드 수신 역할

아래 구분은 합의한 사용자 동작을 설명하기 위한 논리적 역할이다. 실제 실행 파일 수, 프로세스 간 통신 및 실행 관리 방식은 아직 결정하지 않았다.

| 역할              | 담당 동작                                                                    |
|-------------------|------------------------------------------------------------------------------|
| 채팅용 프로세스   | 대화 조회, 메시지 작성·전송, 내 메시지 하이라이트, 상대 상태 표시            |
| 백그라운드 수신기 | 채팅 화면이 닫혀 있어도 메시지 수신·복호화·중복 제거·암호화 저장을 계속 수행 |

### 6.1 화면 종료 후 수신

- 채팅 화면을 닫는 것과 백그라운드 수신기를 종료하는 것은 구분한다.
- 백그라운드 수신기가 실행 중이면 비밀번호 없이 메시지를 받아 수신함에 암호화해 저장한다.
- 다시 채팅 화면을 열면 비밀번호를 입력한 뒤 수신함을 기록에 합쳐 저장된 대화를 조회한다.
- Mac의 잠자기, 네트워크 단절 또는 수신기 종료 중에는 수신을 보장하지 않는다.
- 백그라운드 수신기는 최초 비밀번호 설정 이후 사용자 로그인 항목으로 등록해 로그인부터 로그아웃·종료까지 실행하고, 종료되면 다시 실행한다.
- 로그인 전 수신과 등록 해제 명령은 현재 범위에 없다.

### 6.2 두 역할의 인증

채팅과 기록 조회처럼 기록을 여는 프로세스는 **실행할 때마다 반드시 비밀번호를 입력한다**. 자동 업데이트를 이유로 이 조건을 생략하지 않는다.

백그라운드 수신기는 컴퓨터를 사용하는 동안 계속 실행되어야 하므로 비밀번호 없이 실행한다. 이를 위해 수신기는 기록을 열지 않고, 최초 비밀번호 설정 때 만든 수신함 공개키로만 받은 메시지를 암호화해 쌓는다. 수신함 개인키는 비밀번호에서 유도한 기록용 키로 봉인해 보관하므로, 수신기와 수신함 파일만으로는 받은 메시지나 기록을 읽을 수 없다.

비밀번호나 기록용 키를 자동 제공하는 방식은 승인하지 않는다. 수신기에도 비밀번호·기록용 키·수신함 개인키를 전달하지 않는다.

## 7. 상대 상태와 heartbeat

### 7.1 온라인의 최종 정의

**온라인은 상대의 대화를 읽고 입력하는 채팅용 프로세스가 실행 중인 상태이다.**

- 다른 탭이나 다른 앱을 보고 있더라도 채팅용 프로세스가 실행 중이면 온라인이다.
- 터미널 창이 전면에 있는지, 해당 탭이 선택되었는지는 기준으로 사용하지 않는다.
- 사람이 실제로 화면을 읽거나 메시지를 확인했다는 뜻은 아니다.
- 백그라운드 수신기만 실행 중이면 상대 상태는 오프라인으로 표시한다.

대화 중 검토했던 창·탭 활성화 기준과 수신기 실행 기준은 최종 온라인 정의로 사용하지 않는다.

### 7.2 heartbeat 정책

- 채팅용 프로세스가 실행 중인 상태를 3초 간격 heartbeat로 알린다.
- 첫 heartbeat는 채팅 시작 즉시 송신하고, 이후 마지막 송신 시각을 기준으로 3초 간격으로 송신한다.
- 상대는 마지막 heartbeat 수신 시각을 기록한다.
- 마지막 heartbeat를 받은 뒤 12초 동안 추가 수신이 없으면 오프라인으로 판단한다.
- heartbeat도 공유 대칭키로 암호화하고 검증한다.
- heartbeat는 채팅 메시지로 표시하거나 대화 기록에 저장하는 대상이 아니다.

상태 판정은 heartbeat 수신에 근거한 추정이다. 프로세스 종료와 네트워크 단절을 즉시 구별하지 않으며, 오프라인 전환에는 최대 약 12초의 감지 지연과 표시 갱신 시간이 생길 수 있다.

### 7.3 오프라인 표시 중 전송

- 상대가 오프라인으로 표시되어도 메시지 전송을 허용한다.
- 상대의 백그라운드 수신기가 동작 중이면 메시지를 받아 저장할 수 있다.
- 오프라인 표시만으로 수신 가능 여부를 확정하지 않는다.
- 상대의 수신기까지 종료되어 있거나 네트워크 연결이 없으면 메시지는 누락될 수 있다.
- 이 경우에도 전송 횟수와 누락 허용 정책은 동일하게 적용한다.

## 8. 암호화와 개인 비밀번호

### 8.1 통신용 키

- 두 사람의 프로그램에 같은 공유 대칭키를 내장한다.
- 실행 시 사용자가 통신용 키를 따로 입력하지 않는다.
- 채팅 메시지와 heartbeat의 암호화·검증에 사용한다.
- 내용을 보호하면서 변조도 검증하는 인증 암호화 방식으로 설계한다.

프로그램에 내장된 키는 실행 파일을 가진 다른 사람도 확보할 수 있다. 따라서 프로그램 배포 대상을 두 사람으로 한정하는 전제가 있으며, 내장 키만으로 개인의 신원을 인증하거나 다른 프로그램의 복호화를 원천적으로 막는다고 정의하지 않는다.

### 8.2 개인 기록용 키

- 각 사용자는 자신의 개인 비밀번호를 설정한다.
- 두 사람의 비밀번호는 서로 달라도 된다.
- 개인 비밀번호에서 안전하게 유도한 키로 각자의 로컬 대화 기록을 암호화·복호화한다.
- 통신용 공유키와 개인 기록용 키는 분리한다.
- 통신용 내장 키만으로 개인 기록을 열 수 있는 구조로 만들지 않는다.
- 비밀번호 자체를 그대로 암호화 키로 사용하는 방식은 채택하지 않는다.

이 보호의 목적은 기록 파일과 Hush 실행 파일만 가진 사람이 개인 비밀번호 없이 대화 기록을 바로 읽지 못하게 하는 것이다. 특정 프로그램만 파일을 열 수 있게 하는 독점적인 제한은 아니며, 비밀번호나 기록용 키를 가진 다른 도구도 복호화할 수 있다.

암호화 알고리즘, 비밀번호 기반 키 유도 방식, 라이브러리 및 저장 형식은 아직 결정하지 않았다.

### 8.3 비밀번호 입력 정책

| 상황                       | 요구 동작                              |
|----------------------------|----------------------------------------|
| 최초 사용                  | 개인 비밀번호 설정                     |
| 이후 채팅·기록 조회 실행   | 반드시 비밀번호 입력                   |
| 채팅 화면 재실행           | 비밀번호 입력 후 기록 조회와 채팅 이용 |
| 업데이트 자동 재시작       | 채팅은 반드시 비밀번호 재입력          |
| 백그라운드 수신기 실행     | 비밀번호 없이 수신함 공개키로만 저장   |

- 채팅의 자동 업데이트 재시작도 예외로 처리하지 않는다.
- 비밀번호 입력 전에는 개인 기록을 복호화하지 않는다.
- 기록용 키가 필요한 저장은 잠금 해제 이후에 수행한다.
- 프로세스 재시작을 넘어 잠금 해제 상태를 자동 유지하지 않는다.
- 별도 복구 수단이 없다면 비밀번호 분실 시 기존 기록을 복구할 수 없다.

비밀번호 변경, 복구 수단, 입력 실패 처리 정책은 현재 정의하지 않았다.

## 9. 로컬 대화 기록

- 각 사용자의 Mac에 대화 기록을 저장한다.
- 내가 보낸 메시지와 수신한 상대 메시지를 보관한다.
- 같은 메시지의 반복 수신본을 여러 건으로 저장하지 않는다.
- 메시지의 발신 IP와 생성 시각을 함께 보관하는 방향으로 정의한다.
- 기록은 개인 비밀번호로 보호한 암호화 상태로 저장한다.
- 일반 텍스트 편집기로 기록 파일을 열어 대화 내용을 바로 읽을 수 없어야 한다.
- Hush를 실행하고 비밀번호를 입력한 뒤 이전 기록을 조회할 수 있어야 한다.

저장 위치, 파일·데이터베이스 형식, 보관 기간, 기록 삭제·검색·내보내기와 양쪽 기록 동기화 기능은 아직 정하지 않았다.

## 10. 자동 업데이트

### 10.1 새 버전 발견

- 사내망 배포 주소에서 최신 버전 정보를 조회한다.
- 프로세스 실행 시 한 번 확인한다.
- 이후 실행 중에는 10분마다 확인한다.
- 사용자는 `hush update` 또는 `hush upgrade`로 주기를 기다리지 않고 바로 확인·적용할 수 있다.
- 실행 중인 프로그램 버전과 배포 주소의 최신 버전을 비교한다.
- 최신 버전 정보에는 최소한 버전 번호와 프로그램 파일의 위치가 필요하다.

자동 업데이트는 Hush의 별도 기능으로 정의한다. SPM의 빌드·패키지 관리 기능이 실행 중인 Hush를 자동으로 교체해 주는 것으로 가정하지 않는다.

### 10.2 발견 후 적용

1. 새 버전이 있음을 확인한다.
2. 사내망 배포 주소에서 업데이트 파일을 내려받는다.
3. 업데이트 파일이 신뢰할 수 있는 배포 파일인지 검증한다.
4. 검증한 프로그램으로 교체한다.
5. 다음 실행을 기다리지 않고 즉시 자동 재시작한다.
6. 재시작한 프로세스에서 비밀번호를 다시 입력받는다.

사용자는 업데이트를 발견하면 바로 적용·재시작하는 방식을 선택했다. 업데이트 재시작에 한해서 비밀번호 입력을 생략하거나 잠금 해제 상태를 유지하는 예외는 두지 않는다.

### 10.3 업데이트와 수신·기록

- 업데이트 재시작 시 기존 메모리의 기록용 키를 자동 유지하지 않는다.
- 채팅이 재시작 후 비밀번호 입력을 기다리는 동안 기록용 키가 필요한 저장을 진행하지 않는다.
- 수신기는 비밀번호 없이 바로 재시작해 수신함 저장을 이어간다.
- 수신기 종료·재시작 사이에 수신이 중단되는 짧은 구간의 메시지는 누락될 수 있다.
- 이는 현재 정의한 누락 허용 정책의 제약이며, 별도의 전달 보장 기능을 합의한 것은 아니다.
- 프로그램 교체는 기존 암호화 기록을 제거하는 동작으로 정의하지 않는다.

실제 업데이트 시 교체·재시작할 프로세스 범위, 채팅용 역할과 수신 역할의 갱신 순서, 버전 간 통신·기록 호환성, 실패 시 복구와 파일 검증 방법은 구현 설계에서 정한다.

## 11. 사용자 동작 시나리오

### 11.1 평상시 대화

- 두 사용자가 비밀번호를 입력해 Hush의 채팅용 프로세스를 실행한다.
- heartbeat를 통해 서로 온라인으로 표시한다.
- 메시지는 암호화되어 세 번 전송된다.
- 상대는 중복을 제거해 한 번만 표시·저장한다.
- 발신자는 자신의 메시지가 하이라이트된 것을 확인한다.

### 11.2 상대가 다른 탭을 보는 경우

- 상대의 채팅용 프로세스가 실행 중이면 온라인 상태를 유지한다.
- 실제 창·탭 활성화 여부는 상대 상태에 반영하지 않는다.
- 터미널에서 지원하는 시각적 표시로 새 메시지를 알아볼 수 있다.

### 11.3 상대가 채팅 화면을 닫은 경우

- 채팅용 프로세스가 종료되면 heartbeat 기준에 따라 상대가 오프라인으로 표시된다.
- 상대의 백그라운드 수신기가 계속 동작 중이면 메시지를 받아 암호화해서 저장한다.
- 발신자는 오프라인 표시 상태에서도 메시지를 보낼 수 있다.
- 상대는 나중에 비밀번호를 입력해 채팅 화면을 열고 저장된 대화를 조회한다.

### 11.4 상대 Mac이 잠자거나 연결이 끊긴 경우

- heartbeat가 12초 동안 오지 않으면 오프라인으로 표시한다.
- 이 구간에 보낸 메시지는 수신되지 않을 수 있다.
- 메시지가 누락되더라도 자동으로 과거 메시지를 되찾는 기능은 현재 정의되지 않았다.

### 11.5 실행 중 새 버전이 발견된 경우

- 10분 주기 확인에서 새 버전을 발견한다.
- 파일을 내려받아 검증하고 즉시 교체·재시작한다.
- 자동 재시작 후 비밀번호를 다시 요청한다.
- 비밀번호로 기록을 잠금 해제한 뒤 필요한 기능을 다시 이용한다.

| 실행 인증       | 일반 실행과 자동 재시작 모두 비밀번호를 다시 요구                                      |
| 시각적 표시     | 소리나 시스템 배너를 요구하지 않고 터미널에서 새 메시지 표시 가능                      |
| 업데이트 발견   | 실행 시와 이후 10분 주기로 사내망의 최신 버전 정보를 확인                              |
| 업데이트 적용   | 새 버전 다운로드·검증 후 즉시 교체·재시작하고 비밀번호 재입력을 요구                   |

## 13. 구현 전에 정할 세부 사항

아래 항목은 기능 방향이 불명확해서 작업을 멈춰야 한다는 의미가 아니다. 구현을 요청받았을 때 선택지와 프로젝트 규약을 확인하고 결정할 사항이다.

- 실제 사내망 배포 URL, 배포 파일 제공 방식과 업데이트 검증 방법
- 지원할 최소 macOS 버전과 Apple Silicon·Intel 범위
- Swift 라이브러리, 암호화·키 유도·해시 알고리즘
- 메시지·heartbeat·최신 버전 정보의 형식과 버전 관리
- 통신 포트, 브로드캐스트 주소 선택과 복수 네트워크 인터페이스 처리
- 채팅용 역할과 수신 역할의 프로세스 구성 및 실행·종료 방식
- 각 프로세스 실행 시 비밀번호를 받을 방법과 기록용 키 관리 방식
- 타임스탬프 정밀도와 동일 시각·동일 내용의 별도 메시지 구분
- 로컬 기록 저장 형식·위치와 보관·관리 정책
- 프로그램 버전 간 통신·기록 호환성과 업데이트 실패 처리
- 터미널별 시각적 표시 방식과 설정 안내
